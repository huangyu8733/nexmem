# 分辖区监管合规接口方案（设计稿，暂不实施）

> 目标：按用户所在司法辖区加载对应监管策略，通过可插拔的监管适配器接入当地合规能力，
> 以「预防 + 阻断 + 审计」方式降低平台被用于违法犯罪的风险。
> 状态：**方案阶段**。本轮只写设计，不改代码、不改契约。
> 基线：当前内核契约 97 方法 / 26 事件 / 14 错误码，Flutter 全量 644 通过 + 3 跳过。

---

## 0. 先定红线（决定架构边界）

| 红线 | 含义 | 对架构的约束 |
|---|---|---|
| 不做后门 | 不为任何主体留"绕过加密/绕过审批"的通道 | 执法协助必须走法律文书 + 双人审批 + 审计，不能是 RPC 开关 |
| 端侧优先 | 不在服务端无差别收集消息全文 | 服务端只做元数据风控；内容检测放端侧，命中后只上传必要证据 |
| 尊重加密承诺 | 若消息是端到端加密，服务端无法解密正文 | 服务端只做元数据/哈希/举报后人工审核；CRYPTO 边界写进威胁模型 |
| 数据最小化 | 只收实现合规目的所必需的数据 | 辖区判定用最少信号，审核按需取，不用"全量留存再筛" |
| 境内数据不出境 | 中国大陆用户数据遵守 PIPL / 数据安全法 / 网络安全法 | 适配器按辖区本地化部署，审计日志分区存储 |
| 留存有期限 | 不永久保存已删除内容 | 每类数据按辖区策略设 retentionDays，到期硬删 |
| 可申诉 | 误判不能没有救济 | 每个 BLOCK / REVIEW 都给申诉入口与人工复核队列 |

**明确不做**：无差别监控、批量导出用户聊天、静默监听、绕过法律程序的"协助请求"、
用 IP 单一信号直接定性、把用户位置/身份卖给第三方。

## 1. 总体架构

```
用户动作
  │
  ▼
[客户端 Flutter] ──功能开关/提示/举报/申诉──┐
  │                                          │
  ▼                                          │
[内核 Go gateway] → 策略前置钩子 pre-hook ────┤
  │                    │                      │
  │                    ▼                      │
  │            [PolicyEngine]                 │
  │              ├─ 辖区识别 JurisdictionResolver
  │              ├─ 策略包 PolicyPack（签名/版本/灰度）
  │              └─ 判定 Verdict: ALLOW/WARN/BLOCK/REVIEW/KYC
  │                    │                      │
  │                    ▼                      │
  │            [RegulatoryAdapter 注册表]     │
  │              CN / EU / US / SG / default   │
  │                    │                      │
  ▼                    ▼                      ▼
业务执行          审计日志(append-only)    事件回推客户端
```

三层分离，避免把"国家差异"散落在业务代码里：

1. **识别层**：判断这次请求适用哪个辖区。
2. **决策层**：用该辖区的策略包做评估，输出统一 Verdict。
3. **执行层**：内核 / Web 网关 / 客户端三个执行点，按 Verdict 行动；适配器封装国家差异。

## 2. 辖区识别（JurisdictionResolver）

### 2.1 信号源与权重

| 信号 | 强度 | 说明 |
|---|---|---|
| 实名核验返回的国籍/地区 | 强 | 最权威，需 KYC 后才有 |
| 注册手机号国家码 | 强 | 现有账号体系可扩展字段 |
| 支付/账单地区 | 强 | 若接入支付 |
| 服务端 IP 归属地 | 中 | 复用已有 ip2region xdb（服务端权威库，非客户端本机推断）；VPN/代理会误判 |
| 用户主动选择的国家 | 中 | 可改，但需记录变更历史 |
| 系统语言 / 时区 | 弱 | 仅作辅助，不作为唯一依据 |

### 2.2 冲突与移动规则

- 多信号冲突时按强度排序；强信号之间冲突 → 进入 `PENDING_VERIFICATION`，**默认套用最严格策略包**，提示用户确认。
- 账号辖区为主，短期跨国旅行（IP 变化 ≤ N 天）不改策略；持续在另一辖区超过阈值才触发复核。
- IP 判定永远不单独定性，只作为"提示复核"信号。
- 客户端已有的「自动归属地」开关只用于本机地图标注，**不参与监管辖区判定**（本机推断不可作为合规依据）。

## 3. 策略包（PolicyPack）

### 3.1 结构

```json
{
  "jurisdiction": "CN",
  "version": 7,
  "effectiveAt": 1795800000000,
  "signature": "ed25519:...",
  "rules": {
    "features": { "groupChat": true, "fileShare": true, "voiceCall": false },
    "limits": { "msgBytes": 4096, "groupMembers": 200, "dailySends": 500 },
    "moderation": "PRE_SEND",
    "kycLevel": 2,
    "retentionDays": { "message": 90, "audit": 365, "report": 1095 },
    "reportEndpoint": "cn-compliance-adapter",
    "allowedFileTypes": ["image/*", "application/pdf"]
  }
}
```

`moderation` 四档：`OFF`（仅举报）/ `POST_SEND`（先发后审）/ `PRE_SEND`（先审后发）/ `BLOCK_ALL`。

### 3.2 生命周期

- 内核启动时 `policy.getPack` 拉取，校验 Ed25519 签名 + 版本 + 生效时间；失败则加载本地缓存上一版。
- 缓存也没有 → 使用 `default_pack`（最保守：功能全开但审核 PRE_SEND、KYC 要求最高、留存最短），**fail-closed 只针对高风险动作**，普通聊天不阻断。
- 事件 `policy.changed` 推送客户端，UI 提示"监管策略已更新"，功能入口重新计算。
- 灰度发布按 `jurisdiction + accountHash % 100` 分批，支持一键回滚到上一版本。

## 4. 监管适配器（RegulatoryAdapter）

### 4.1 统一接口（Go）

```go
type RegulatoryAdapter interface {
    Jurisdiction() string
    VerifyIdentity(ctx context.Context, req IdentityRequest) (KYCResult, error)
    Moderate(ctx context.Context, req ModerationRequest) (Verdict, error)
    SubmitIllegalReport(ctx context.Context, r Report) (Receipt, error)
    HandleLegalRequest(ctx context.Context, lr LegalRequest) error
    RetentionDays(kind string) int
}
```

### 4.2 辖区实现矩阵

| 辖区 | 适配器 | 核心能力 | 依据/渠道（需资质与合同） |
|---|---|---|---|
| 中国大陆 | `cn_adapter` | 实名核验、内容安全 API、违法线索举报、数据本地化 | 网络安全法 / PIPL / 反电信网络诈骗法；对接合规云审核服务与举报渠道 |
| 欧盟 | `eu_adapter` | DSA 透明度、GDPR 删除权、年龄门槛、举报 | DSA / GDPR；通知-删除流程 |
| 美国 | `us_adapter` | COPPA 年龄门槛、NCMEC 举报 | COPPA；未成年人保护举报渠道 |
| 新加坡 | `sg_adapter` | 实名、内容移除、举报 | 本地监管要求 |
| 其他/未覆盖 | `default_adapter` | 只做规则检测 + 人工审核队列 + 举报 | 最保守策略，不自动执行封禁 |

适配器可插拔：**没有第三方资质/密钥时不接入真实 API，只落人工审核队列**，不伪造合规能力。

## 5. 执行点

### 5.1 Go 内核 gateway（主执行点）

在统一分发层加策略中间件，不必逐方法改业务代码：

- `pre`：对 `dm.sendText` / `dm.sendFile` / `dm.sendGroupText` / `group.create` /
  `fs.publish` / `contact.add` 等做评估，命中 `BLOCK` 直接返回 `POLICY_BLOCKED`。
- `post`：对 `msg.list` / `conversation.list` 做输出过滤，隐藏被判违规且未申诉通过的内容。
- 重活（内容审核 API 调用、模型推理）异步化，pre-hook 只做轻量判定，避免同步 RPC 超时（吸取 `fileSendTimeout` 的教训）。

### 5.2 Web 网关 nexmem-webd

建立 `/ws` 连接、`/upload`、`/download` 时校验辖区、KYC 状态与文件类型/哈希；
命中策略返回结构化错误码，不静默失败（参考 Web token 错误的修复经验）。

### 5.3 Flutter 客户端

- 功能入口按 `features` 开关显示/隐藏，禁用时给出**可翻译的原因文案**（不是空白点击）。
- 新增「举报」「申诉」入口，提交到 `report.submit` / `appeal.submit`。
- 命中 `KYC_REQUIRED` 时引导完成核验，而不是让用户反复点发送。
- 复用现有注入模式（如 `RemoteGeoController` 的注入点）方便测试。

### 5.4 端侧内容检测

- 本地维护增量违规哈希库（图片/文件）和文本规则，命中后才上传必要证据。
- 视频/音频抽取特征帧上传，不上传原始全量文件。
- 端侧模型更新走签名策略包，避免被篡改。

## 6. 执法协助与审计（最容易被做错的部分）

**流程**：收到请求 → 校验法律文书（辖区、案号、机关、签章）→ 法务初审 +
第二人复核 → 按"最小必要"导出指定数据 → 加密交付 → 全程写审计链。

- 审计日志 append-only，记录：谁发起、依据文书、审批人、导出范围、时间、哈希。
- 审计链用 HMAC 串联，防篡改；留存期按辖区策略，到期归档/删除。
- 定期发布**透明度报告**（只发数量与类型，不披露个人信息）。
- 任何"直接查某人聊天"的接口都必须走这条流程，不提供快捷 RPC。

## 9. 测试要点

- 辖区识别：强/弱信号冲突、VPN IP、跨国旅行、待确认默认最严。
- 策略包：签名失败、过期、版本回退、灰度分组、离线缓存、fail-closed 边界。
- Verdict 全分支、审核接口超时降级、同步 RPC 不超时。
- KYC 状态机、执法请求缺文书被拒、双人审批缺一人被拒。
- 审计链：篡改检测、留存到期删除、跨境分区隔离。
- Flutter：功能开关 UI、举报/申诉表单、六语文案、错误码提示。
- 契约 baseline 用例 + 方法数断言 + Web 网关策略钩子集成测试。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 误判影响正常用户 | 观察模式先行、人工复核、申诉通道、按辖区灰度 |
| 隐私争议 | 端侧优先、数据最小化、留存期限、用户告知 |
| 跨境数据违规 | 辖区本地化存储、境内数据不出境、审计分区 |
| 与端到端加密冲突 | 明确 CRYPTO 边界：服务端只做元数据/哈希/举报后人工 |
| 第三方资质未就绪 | 适配器降级为人工队列，不伪造合规能力 |
| 审核拖慢消息 | pre-hook 轻量化 + 异步队列 + 超时降级 |

## 11. 需要你先确认的决策

1. **首批辖区**：先做中国大陆，还是 CN / EU / US 三个并行？
2. **第三方供应商**：是否已有实名核验 / 内容审核服务商及资质、密钥？没有则 P2 只能人工队列。
3. **执法协助渠道**：实际接收请求的入口是什么（邮箱 / 门户 / 专线）？
4. **加密边界**：产品是否对外承诺端到端加密？这决定内容审核能做到哪一层。
5. **观察模式**：能否接受 P0 只记录不阻断、跑一段时间再开阻断？
6. **前端策略**：是否允许客户端缓存策略包离线运行（体验好但存在被篡改风险）？

确认后我再按 P0 开始实施，先把契约和观察模式骨架落地。
