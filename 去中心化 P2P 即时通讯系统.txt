# 去中心化 P2P 即时通讯系统（用户自托管离线存储版）工程方案
> 核心原则：在线全网 P2P、离线自给自足、平台零消息存储

## 一、系统总体架构与核心设计边界
本系统将所有安装客户端的设备构建为完全平等的 P2P 节点，不设中心消息服务器、官方消息中转服务或官方消息存储库。实时在线通信与离线消息投递采用双轨解耦架构，确保平台不持有任何聊天明文，也不承担消息存储成本与内容中转带宽成本。

- **客户端应用层（全功能对等节点）**：每台终端设备作为一个独立的 P2P 节点运行，内部划分为本地 SQLite 存储模块、libp2p 网络通信栈模块以及 S3 离线存储客户端模块三大核心组件。
- **点对点实时通信层**：所有在线私聊、在线群聊、文件传输及音视频通话均通过 libp2p 建立点对点加密通道直连收发，数据流不经过任何第三方服务器转发。
- **自托管离线存储层**：离线消息能力完全由用户或群组自主决定并自行提供 S3 兼容云存储，私聊离线消息由接收方自备云存储承载，群聊离线消息由群主或管理员配置的群云盘承载。
- **轻量级公钥与配置索引层**：系统唯一保留的轻量中心化组件仅作为公开目录服务器，负责维护节点与群组的公钥及加密存储配置映射，不存消息、不解密、不中转且不备份。

## 二、技术栈选型与数据协议规范
为保障跨平台稳定性与底层网络穿透性能，客户端与服务端组件采用成熟的高并发及系统级技术栈组合。

### 技术栈选型
1. 桌面端优先技术方案：底层网络核心基于 rust-libp2p 构建，图形界面采用 Tauri 结合 Vue3 或 React 开发，兼顾低内存占用与高安全性。
2. 跨平台全端技术方案：底层 P2P 核心采用 go-libp2p 编写并通过 FFI 接口向上暴露，前端采用 Flutter 实现一套代码同时覆盖 Windows、macOS、Android 与 iOS 四端。
3. 本地持久化与序列化：客户端统一采用 SQLite 存储本地消息缓存、好友关系、群组信息、密钥及配置，全网通信与离线存储统一使用 Protobuf 进行二进制消息编码。
4. 轻量索引服务技术栈：服务端采用 Go、Python 或 Node 语言配合 Redis 及轻量级键值或关系型数据表构建，仅响应高频目录查询请求。

### 四类核心 Protobuf 协议结构
1. **私聊离线消息结构（OfflineMessage）**：包含全局唯一消息标识 msg_uuid、时间戳 timestamp、发送方标识 sender_peer、接收方标识 receiver_peer、接收方公钥加密后的对称密钥 encrypted_key、AES-GCM 加密的消息正文 ciphertext 以及存活时间 ttl_hours。
2. **群离线消息结构（GroupOfflineMessage）**：包含全局唯一消息标识 msg_uuid、时间戳 timestamp、群标识 group_id、发送方标识 sender_peer、群会话密钥 AES-GCM 加密的消息正文 ciphertext 以及存活时间 ttl_hours。
3. **云存储配置结构（StorageConfig）**：包含存储服务端点 endpoint、存储桶名称 bucket、访问密钥 access_key、私有密钥 secret_key 以及对象路径前缀 prefix。
4. **群密钥分发信封结构（GroupKeyEnvelope）**：包含群标识 group_id、成员节点标识 member_peer、用该成员公钥加密的群 AES 密钥 encrypted_group_key 以及用于轮换识别的密钥版本号 key_version。

## 三、去中心化身份、关系链与多端同步方案
系统彻底摒弃中心化账号注册体系，以密码学公私钥对作为用户唯一身份凭证。

1. **无注册账号生成机制**：客户端首次启动时在本地生成一对 ed25519 密钥对，提取公钥哈希值生成全局唯一的 PeerID 作为用户账号，私钥严格限制保存在本地设备中。
2. **本地关系链管理与恢复**：好友列表、好友分组、备注、黑名单以及群成员列表、群备注、群公告均保存在本机 SQLite 数据库中，Kademlia DHT 网络仅负责查询目标 PeerID 当前的网络地址而不保存好友关系。
3. **换机与防丢失备份机制**：由于私钥丢失会导致账号与历史消息彻底无法恢复，客户端提供加密备份包导出功能，用户在更换设备时通过导入加密备份包恢复私钥、好友关系与配置数据。
4. **多设备并行在线同步**：同一身份（同一对密钥）支持在多台设备上同时上线并各自作为独立 Peer 节点运行，私聊多端通过共用同一个私聊 S3 存储桶拉取离线消息并标记已读，群聊多端通过共用群云盘拉取离线群消息，系统不提供跨账号的云端消息漫游。

## 四、P2P 网络寻址、NAT 穿透与中继兜底机制
针对国内复杂的对称 NAT 环境与移动端移动网络限制，网络层设计多级连接建立与回退策略以保障连通率。

1. **Kademlia DHT 节点寻址**：所有在线客户端接入 Kademlia DHT 网络宣告在线并维护分布式路由表，发送方直接通过目标 PeerID 检索对方当前的公网或内网传输地址，不依赖中心服务器查询在线状态。
2. **端到端加密与自动打洞**：节点间建立连接时强制启用 Noise 协议完成双向身份验证与端到端链路加密，并优先执行 UDP 与 TCP 自动打洞以建立点对点直连通道。
3. **Circuit Relay v2 分布式中继回退**：当双端处于对称 NAT 或受限内网导致打洞失败时，连接自动回退至 Circuit Relay v2 模式，由网络中自愿开启中继功能的在线客户端节点或官方部署的少量兜底 Relay 节点转发加密流量。
4. **移动端功耗与流量保护**：由于开启中继会持续消耗上行带宽与设备电量，客户端将 Circuit Relay 设为可配置开关且默认处于关闭状态，仅在桌面端或用户自愿开启时生效。
5. **索引服务器故障隔离**：轻量索引服务器仅维护 PeerID 到用户公钥、PeerID 到加密私聊 S3 配置包、GroupID 到加密群云盘配置包三类映射，即使索引服务器宕机也仅影响离线消息目录查询，在线 P2P 聊天完全不受影响。

## 五、单聊全链路流转与客户端可靠性机制
单聊模块根据接收方实时网络状态自动在 P2P 直连流与 S3 离线投递链路之间切换，并由客户端闭环实现消息可靠性。

### 1. 双方在线直连流程
发送方通过 Kademlia DHT 查找到接收方当前在线节点地址。
发送方与接收方直接建立受 Noise 协议保护的 libp2p 加密传输流。
文本、表情、图片、文件、语音及音视频流直接在两端之间点对点收发，全程不访问索引服务器且不写入任何云存储。

### 2. 接收方离线投递流程
发送方通过 DHT 探测判定对方离线，或尝试 P2P 打洞及中继连接均失败后，向轻量索引服务器发起查询，检查接收方是否公开了私聊 S3 存储配置包。

- 若接收方未配置云存储或已关闭对外公开开关，客户端立即中止投递并在界面提示“对方未开启离线存储，消息仅支持在线发送，请稍后重试”，消息不在任何远端落地。
- 若接收方已公开存储配置，发送方在本地随机生成一次性 AES-GCM 对称密钥加密消息正文，随后使用从索引服务器获取的接收方公钥加密该 AES 密钥，封装为完整的 OfflineMessage 数据包。
- 发送方直接调用接收方配置包中的受限 S3 凭证，将加密数据包上传至接收方存储桶的 `im_offline/{接收方PeerID}/{msg_uuid}.msg` 路径下。
- 上传成功后客户端界面提示“离线消息投递成功”，若遇到存储欠费、权限错误、存储桶被删或网络异常则返回投递失败提示。

### 3. 接收方重新上线收取流程
接收方启动客户端重新接入 DHT 网络并宣告节点在线。
客户端使用本地保存的自身 S3 存储凭证，自动轮询自身存储桶中 `im_offline/` 目录下的未读消息对象。
客户端将密文包下载至本地，先用本机私钥解密出 AES-GCM 对称密钥，再解密出消息明文并写入本地 SQLite 展示到聊天界面。
解密并入库成功后，客户端自动调用 S3 接口删除已读密文对象，或交由 S3 存储桶预设的生命周期策略到期自动清理。

### 4. 客户端消息可靠性保障机制
- 唯一标识与防重放：每条消息生成全局唯一的 msg_uuid 并附带发送时间戳，接收端结合本地 SQLite 缓存校验时间戳有效性与 msg_uuid，实现严格的消息去重、保序排列与防重放攻击。
- 确认回执与断线同步：在线 P2P 会话内置应用层 ACK 确认回执与超时自动重传机制，当底层网络发生闪断或切网时自动执行重连，并在会话恢复后自动补发同步未收到 ACK 的消息。

## 六、去中心化群聊与群云盘离线协同机制
群聊采用“在线 GossipSub 泛洪广播 + 离线群云盘单副本托管”架构，在保证去中心化的同时避免发送方按群成员人数重复上传造成的带宽爆炸。

### 1. 在线群聊泛洪广播
群组不设中心转发服务器，所有群成员客户端订阅对应群组的 GossipSub 主题，在线消息通过相邻节点间泛洪传播覆盖全群在线成员。
每条群广播消息均携带群 ID、发送方 PeerID、消息指纹以及 TTL 跳数限制，各成员客户端依据消息指纹执行本地去重，并通过 TTL 限制广播范围以遏制无限泛洪开销。

### 2. 群会话密钥生命周期管理
- 密钥生成与初始分发：群主或管理员为每个群组生成随机的群会话密钥（Group AES Key），并使用每位群成员的公钥分别加密该群密钥，通过 P2P 加密通道点对点下发给对应成员，成员用本地私钥解密后存入本地 SQLite。
- 新成员入群授权：新成员加入群聊时，管理员使用新成员公钥加密当前版本的群会话密钥并下发，默认群策略不向新成员开放入群前的历史离线消息回溯权限。
- 退群与踢人前向安全轮换：当有成员退群或被管理员踢出时，管理员立即生成新版本的群会话密钥（递增 key_version），并仅使用剩余群成员的公钥重新加密分发，使离群成员持有的旧密钥无法解密轮换后的任何新群消息。

### 3. 群离线消息单副本投递与拉取
- 未开启群云盘分支：若群主或管理员未配置群云盘，群消息仅通过 GossipSub 在线广播，离线成员上线后无法补收历史消息，群聊界面常驻提示“该群未开启离线消息，仅在线成员可见”。
- 已开启群云盘写入流程：发送方在群内发送消息时先通过 GossipSub 执行在线广播，同时在本地用当前群会话密钥以 AES-GCM 算法加密消息正文，将生成的单份密文上传至群云盘的 `group_offline/{group_id}/{msg_uuid}.msg` 路径下，若上传失败不影响在线广播，仅在本地提示离线兜底不可用。
- 群成员上线拉取流程：群成员上线接入 DHT 并订阅群主题后，使用本地保存的群云盘凭证拉取 `group_offline/{group_id}/` 目录下尚未读取的密文文件，用本地对应版本的群会话密钥解密后渲染至群聊界面，标记已读后可清理本地副本或交由 S3 生命周期策略定期清理。

## 七、云存储接入规范、最小权限与安全模型
为防止用户或群主的云存储凭证泄露带来安全或账单风险，系统在存储接入层实施严格的权限隔离与双重加密机制。

1. **广泛兼容 S3 对象存储**：私聊云存储与群云盘统一支持阿里云 OSS、腾讯云 COS、Cloudflare R2（具备高免费额度，优先推荐用户使用）、Backblaze B2、自建 MinIO 以及个人 NAS 的 S3 服务。
2. **私聊存储强制最小权限策略**：引导并强制用户创建专门用于 IM 离线消息的独立存储桶，且必须使用仅具备 `im_offline/*` 前缀读写权限的受限子密钥，严禁填入具有全局存储桶读写或管理权限的主密钥，同时提供一键关闭“对外公开我的存储配置”功能以随时阻断外部写入。
3. **群云盘目录隔离与权限分层**：群云盘支持使用独立存储桶或在群主自有存储桶下通过 `group_offline/{group_id}/` 独立前缀进行隔离，子密钥仅授权读写对应群前缀且严禁跨群访问；群管理员拥有配置、修改、移除群云盘及解散清理密文的权限，普通群成员仅持有加密后的受限读写凭证而不接触主密钥。
4. **端到端双重加密防护**：首先，用户的 S3 访问凭证（AK 与 SK）在客户端本地保存及上传索引服务器前均经过加密封装，平台索引服务器无法解密获取凭证；其次，写入存储桶的每条离线消息均经过接收方公钥或群会话密钥的 AES-GCM 加密，即便云存储被第三方访问也无法还原聊天明文。
5. **存储与流量费用透明告知**：私聊离线消息的上传与下载流量计入接收方的云存储账单，群离线消息的流量与存储占用计入群云盘所属方（群主）的账单，客户端必须在存储配置页向用户和群主展示明确的计费归属提醒。

## 八、从零到一分阶段落地实施路线
项目按模块依赖关系划分为六个递进阶段实施，确保每个阶段均可独立验证闭环。

- **阶段一（P2P 基础网络连通）**：跑通基于 libp2p 的双节点点对点文本收发最小原型，接入 Kademlia DHT 实现基于 PeerID 的在线节点寻址，并集成 Noise 协议完成传输加密与节点身份验证。
- **阶段二（业务消息与可靠传输层）**：完成文本、表情、图片、文件及语音的 Protobuf 协议定义，在客户端开发消息 ACK 回执、超时重传、时间戳防重放与去重保序逻辑，并基于本地 SQLite 实现消息缓存与好友列表、备注、黑名单的本地存储。
- **阶段三（私聊自托管离线消息闭环）**：集成 S3 客户端实现指定前缀密文的上传、列举与删除，开发 AES-GCM 结合接收方公钥的混合加密模块，部署轻量索引服务器提供公钥与加密存储配置查询，打通接收方上线拉取、解密展示、已读清理及未配置存储时的友好降级提示。
- **阶段四（去中心化群聊与群云盘离线）**：接入 GossipSub 实现群主题订阅、消息泛洪广播、指纹去重与 TTL 控制，开发群会话密钥生成、成员公钥加密下发、入群授权及退群密钥轮换机制，并完成群云盘单副本离线写入、成员上线拉取解密及未开启群离线时的 UI 提示。
- **阶段五（NAT 穿透优化与中继兜底）**：完善 UDP 与 TCP 自动打洞策略，实现客户端 Circuit Relay v2 功能开关化（默认关闭、自愿开启），同时部署少量官方兜底 Relay 节点，实现打洞失败自动回退至中继链路。
- **阶段六（多端打包与用户体验打磨）**：完成桌面端与移动端多平台构建打包，上线私钥与关系链加密备份导入导出、主流云厂商（Cloudflare R2、MinIO、阿里云 OSS、腾讯云 COS）接入引导页、本地消息全文搜索以及断线自动重连状态提示。

## 九、生产环境稳定性保障与合规风控措施
针对去中心化架构在生产运行中的固有挑战，需在工程实现与运营层面落实以下风控措施。

1. **完全自研协议红线**：从底层身份生成、网络寻址到上层消息协议全部采用自研方案，严禁逆向任何现有商业即时通讯软件（如 QQ、微信等）的私有协议。
2. **分布式链路可观测性**：针对 P2P 消息链路分散、难以集中排查的问题，在客户端内置本地结构化诊断日志（记录 DHT 路由收敛耗时、打洞成功率、中继回退状态与 S3 响应码），支持用户自主导出脱敏诊断日志辅助排障。
3. **国内合规备案与举报处置**：若面向国内公众提供社交服务，必须依法完成 ICP 备案与公安网安备案，并在客户端应用内提供明确的违规内容举报入口与本地拉黑、屏蔽等处置通道，履行平台内容管理责任。
